# 需求追踪矩阵（对照《tg-gy 最终版项目开发需求文档 V1.0》/《V2.0》）

> 版本基线：`v0.8.9`（2026-11-18）；v0.8.7 commit `aa1f32c`，v0.8.6 commit `ae62a3c`，v0.8.5 commit `414ac5d`，v0.8.4 commit `beed009`，v0.8.3 commit `0d7afff`，v0.8.1 commit `b99ec77`，v0.8.0 基线 commit `663d1fe`
> 状态口径：**只按代码与测试的实际状态填写**，不把「写了页面」「写了字段」算作完成。
> 条款编号以原始需求文档为准，本表按能力域归组，便于逐条打勾复核。

## 图例

| 标记 | 含义 | 判定标准 |
| --- | --- | --- |
| ✅ 已实现 | 主链路闭环 | 代码 + 单元测试/契约测试同时覆盖，且不依赖未验证的外部接口 |
| 🟡 部分实现 | 代码存在但闭环有缺口 | 有实现，但依赖人工步骤、外部真实环境，或隔离只靠约定没有数据层强制 |
| ⏳ 待验证 | 接口已按文档实现 | URL/请求体有契约测试，但没有真实账号/真实返回的联调记录 |
| ❌ 未实现 | 明确未做 | 缺少已验证接口，按需求文档 8.6 保留为待验证，**不猜测参数** |

结论先行：**主干能力已实现并有 215 项回归测试覆盖；v0.8.8 修掉「补复制回来的文件是中文原名却因 DB 残留改名状态被整批跳过」的问题，改名改为以 B 库实际文件名为准并补齐跳过原因诊断；v0.8.7 修掉「B 库影视文件夹下为空目录」的根因（DB 标记 `synced` 不等于 B 库真有文件，改为每轮只读核对并自动补复制），统一三个刷新入口按 B 库实际内容重建资源库，并补齐多层分类树 1:1 镜像；v0.8.6 按用户实测反馈把 B 库单集 / 单电影文件名改为英文剧名（只换中文片名段，A 库与 B 库目录名不动，A→B 映射靠文件 ID + 指纹保持）；v0.8.5 按用户明确口径接通「镜像完成 → 刷新入库 → 识别 → 只推本轮识别成功且有海报的影视」，反转了 v0.8.0~v0.8.4 写死的「镜像完成不自动推送 Telegram」红线，但保留了「不是群推送」的边界（不批量补推历史内容变化事件）**。v0.8.4 修掉「B 库目录建好、命名正常，但文件没镜像过去」，v0.8.3 修了 `*` → `·`、根目录重复配置与日志膨胀，v0.8.2 修了建目录失败诊断，v0.8.1 落地 HAR 取证的写接口，但仍不能声明「全面功能实现」。剩余缺口集中在三类：① **投稿分享转存与 `copy_file` 都没有真实抓包**（`copy_file` 目前只有前端 JS 调用契约，原始 `w.har` 54 条请求里没有一次复制操作）；② 真实 A/B 网盘、TgtoDrive、Telegram Bot 的联调（尤其自动链路在真实环境下的识别/推送结果、电影目录分享的真实链接、`·` 目录名兼容性）；③ 推送隔离的数据层字段。详见文末「未完成项清单」与 `docs/光鸭接口取证.md` 第十、十一节。

## v0.9.0 规划（已接住需求，未实现）

用户新需求：① 分发中心与互动中心合并；**TG Bot 只承担「转存 / 搜索 / 求片」三个功能**，注册、签到、抽奖、兑换码、积分、邀请码等 embyhub 玩法**仅作为视觉风格与卡片式按钮布局的参考，不实现功能**；Bot / 频道 / 群聊三者配合参考 `Abson2/embyhub`；② 保持现有功能不删的前提下做整站 UI / 视觉 / 交互重构，目录结构、卡片式按钮菜单与页面布局参考 embyhub 与用户截图；③ 主干链路不变（光鸭网盘 → TMDB 识别 → 自建分享 → TG Bot / 频道 / 群聊）。

已完成的调研：embyhub 采用双 Bot（`user_bot` 用户私聊 + `notification_bot` 频道推送）、`setMyCommands` 注册斜杠命令、`ub_menu_*` inline keyboard 菜单与 callback 路由、`/bind_channel` 把频道身份绑定到用户账号。ya-tg 当前 Bot **只有 send 能力，没有 getUpdates / Webhook 接收链路**，且无用户体系；要实现「搜索 / 求片 / 转存」的双向交互，必须先补消息接收入口与 callback 路由，不需要引入签到 / 积分 / 抽奖等用户体系数据表。

阻塞项：用户提供的截图均为内联附件，本地多次检索未落盘，无法精确复刻布局；需用户提供本地文件路径后再做视觉重构。

### 求片流程（用户明确「不要太复杂」，到此为止）
1. 用户点「📝 求片」→ 输入片名 → Bot 发**二次确认**（inline keyboard 确认 / 取消）；
2. 确认后生成求片单落库，管理员在管理页审核（通过 / 拒绝）；
3. Bot **回复用户**审核结果；
4. 通过后把**搜索到的资源转存到 A 库** → 复用现有「A→B 镜像 → 入库 → 识别 → 分享 → TG 推送」链路自动推送。

不做积分、配额、多人审批、排行榜、复杂通知模板、自动搜刮策略。

### 菜单信息架构（用户授权「你看着办」，此处定稿）
- 分发中心与互动中心**合并为一个模块**，内部两区：①「频道 / 群聊分发」（现有 Bot / 频道 / 分发规则 / 推送模板）；②「Bot 交互」。
- Bot 主菜单三个平级按钮：`🔍 搜索资源` / `📝 求片` / `📥 转存`。
- **求片与转存分开成两个入口**：求片是带二次确认 + 审核状态机的长流程，转存是给链接即时执行的动作；合并会让状态机互相干扰。两者只在「转存到 A 库」这一步复用同一实现。
- 视觉只借鉴 embyhub 的卡片式两列按钮网格、`ub_menu_*` callback 路由与 `setMyCommands` 斜杠命令注册，不引入其账号 / 签到 / 积分体系。

### 三、数据层隔离缺口（真实环境才会暴露，非本次能闭环）
- `QueueItem` / `DistributionEvent` 无 `source/mode` 字段；「镜像不群推」靠模块级约定 + 作品级去重保证，**没有数据层强制**。
- 镜像后 B 库扫描产生的 `DistributionEvent`（`queue_id=0`）会留在库里；后续任意一次常规扫描 / 重新扫描库调用 `process_change_events(publish=True)` 时，可能被处理成一次作品级更新推送。
- 验证方法：镜像同步完成后，先不要点资源库「立即扫描」；观察一段时间确认无自动推送；再手动点一次「立即扫描」，看是否冒出一条「作品级更新」推送——若有，即为此缺口，需要加来源字段才能彻底隔离。
- 结论口径：**不能宣称「镜像变化永不自动推送」**，只能说「当前默认路径不推」。

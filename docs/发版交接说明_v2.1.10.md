## 二、本版四条主线（都是用户真机报障的真实故障）

**① 镜像流水线互斥串行**（用户口径：上一轮没跑完，下一轮定时任务不启动）
- 根因：镜像轮次与定时扫描轮次**各跑各的**，定时扫描**完全没有锁**——一边按旧名入库、镜像一边改 B 库文件名。
- 修法：新增等待式闸门 `acquire_async(owner, timeout)`；四个定时入口全部纳入同一把闸门；手动端点保持 409 明确拒绝。
- 一轮的完结口径：**复制 → 改名 → 翻译 → 识别 → 入库到资源库**，全走完才算完结。

**② 光鸭 code=160「假失败」幂等收敛**（真实缺陷：文件早已改名成功，却报失败并露出矛盾状态）
- 160 = 目标名已存在，与 127（瞬时限流）是两回事：127 退避重试，160 **重试无用**，只能幂等收敛。
- 语义二分：同一 fileId 已是该名 → 收敛为完成并清两个错误位；别的文件占了该名 → 真冲突，走冲突后缀重试。
- 展示文案中性表述，**不露 code 值**；160 不做退避重试。

**③ 改名门禁收敛到作品级**（真实缺陷：1 部剧的 1 个假失败让 20 部全没入库）
- 根因：v2.1.0 的硬门禁是「任一文件改名失败即整轮跳过入库→识别→推送」。
- 修法：整轮拦截默认关闭（`RENAME_GATE_BLOCK_WHOLE_ROUND = False`，一行可回退）；改由**推送侧作品级闸门**兜底。

**④ 资源库识别与展示改用「映射回 A 库」+ 电影/剧集类型锁定**
- `resources` 表加 5 列（老库自动 ALTER 补齐）：`source_title` / `source_name` / `source_tmdb_id` / `source_media_type` / `source_category`。
- 识别线索改口径：文件名用 A 库原名，目录线索 = B 库目录链 + A 库分类目录链 + A 库作品名置于末尾。
- 类型锁定防串台：TMDB 的 movie / tv 是**两套独立 ID 命名空间**；`identify()` 新增 `forced_tmdb_id` / `forced_type`，**ID 阶段与名称阶段双锁同一命名空间**。
- 类型判定三级（文件身份 → 分类目录 → 作品字段），**判不出就留空绝不猜**。
- 回填接在识别之前；启动即回填老库存量 + 每 10 分钟补一次。四处识别入口统一走 A 库线索。
- 展示层同步（含**手动修正的输入窗口**）：只给中性文案，**不露任何后端字段名**。

## 三、部署步骤

```bash
# 1) 备份（升级前必做）
mkdir -p ./backup
cp -r ./db ./backup/db && cp -r ./logs ./backup/logs
cp -r ./data ./backup/data 2>/dev/null || true   # Telegram 登录会话（等同账号凭据）

# 2) 指定版本
# .env: IMAGE_TAG=v2.1.10

# 3) 拉取并重启
docker compose pull && docker compose up -d

# 4) 确认版本
curl -s http://<host>:8787/api/health    # 应返回 "version":"2.1.10"
```

⚠️ **必须补挂 `./data` 卷**（v2.1.8 起新增，不挂则「阅读量」页永远显示「未就绪」）：
```yaml
volumes:
  - ./db:/app/db
  - ./logs:/app/logs
  - ./data:/app/data      # ← 必挂
```
宿主 `./data` 目录属主须为 `10001:10001`（`chown -R 10001:10001 ./data`）。

**本版新增的老库变更（自动执行，无需手工干预）**：
- `resources` 表 ALTER 补 5 列（`source_title` / `source_name` / `source_tmdb_id` / `source_media_type` / `source_category`）。
- 启动即回填老库存量的 A 库映射；之后每 10 分钟补一次新入库未匹配上映射的行（幂等，只补空映射）。

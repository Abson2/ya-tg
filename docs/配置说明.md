## 一、光鸭认证：两套体系不能混用

这是最容易踩的坑，配置前务必分清。

| | 网页端账号服务（普通用户用这个） | 官方 OpenAPI（高级用户） |
| --- | --- | --- |
| 域名 | `account.guangyapan.com` / `api.guangyapan.com` | `openapi.guangyapan.com` |
| 登录方式 | 手机号 + 短信验证码 | Device Code / Web PKCE |
| 凭证 | `access_token` + `refresh_token` + `did` | 开放平台应用凭证 |
| 业务接口认证头 | `Authorization: Bearer {token}` + `did` + `dt:4` | `x-client-id`（应用 ID）+ Bearer |
| 是否要去开放平台申请应用 | **不需要** | 需要，含 `project_id` / `sign_secret` |
| 本项目用途 | 文件列表、建/改/删分享、复制与建目录、任务状态 | 仅特定高级功能 |

- 普通用户只需在管理页「光鸭授权」输入手机号收验证码，凭证自动加密保存并到期刷新。
- 网页公开页面里的 `client_id`（形如 `aMe-8VSlkrbQXpUR`）**不是**开放平台应用 ID，不能拿去调官方 OpenAPI 业务接口，会报 `code=120`（应用 ID 错误）；反过来用短信凭证调官方 OpenAPI 也一样报错。
- `GuangYaOpenAPI._call` 有前置 guard：网页端凭证且没有 `client_id` 时直接报中文提示，防止错配漏出。
- 授权状态里的手机号 / 账号已脱敏（`utils.mask_account()`），`client_id` 属于应用 ID 不属于个人隐私，保留明文。

### 本项目实际调用的光鸭网页端接口

```http
POST /userres/v1/file/get_file_list   {"page":1,"pageSize":100,"parentId":"*","needSubFolderStat":true}
POST /userres/v1/share_file           # 创建分享
POST /userres/v1/update_share         # 修改分享
POST /userres/v1/delete_share         # 删除分享链接（不是删文件）
```

镜像复制（需求文档第八章确认）：

```http
POST /userres/v1/file/copy_file  {"fileIds":["..."],"parentId":"..."} → data.taskId
POST /userres/v1/get_task_status {"taskId":"..."}                     → data.status
```

v0.8.1 抓包 HAR 确认并落地的写接口：

```http
POST /userres/v1/file/create_dir   {"parentId":"...","dirName":"..."} → data.fileId
POST /userres/v1/file/rename       {"fileId":"...","newName":"..."}
POST /userres/v1/file/delete_file  {"fileIds":["...","..."]}          → data.taskId
```

- `create_dir` 用于 **A→B 目录自动镜像**；`rename` / `delete_file` 接口能力已具备，但主链路不调用（目录直接按目标名创建，且需求禁止「先删旧再复制」）。
- `status=2` 表示任务完成；**其它取值只原样记录 `raw_status` 并标 `unknown`，不猜成功或失败**，可在「镜像同步 → 继续轮询」里继续查。
- 没有 `taskId` / `fileId` 返回时直接报错，不标记完成，避免假成功。

### 仍未验证、因此未实现的接口

**只剩「投稿分享转存」**（TgtoDrive 侧 / 光鸭转存链路，本次 HAR 没有相关请求）。因此投稿只登记审核，不自动转存入库、不写 B 库、不触发推送。

前端 JS bundle 里还出现 `move_file` / `recycle_file` / `clear_recycle_bin` 等路径，但**只有字符串、没有请求体，本项目不实现、不猜参数**。详见 [光鸭接口取证](光鸭接口取证.md) 第四节。

## 二、A/B 目录 ID 怎么填

管理页「镜像同步 → A / B 库设置」需要两个 ID：

- **A 源头库目录 ID**：只读遍历的起点，存放原始资源。
- **B 镜像库目录 ID**：复制目标，也是扫描、资源库、分享、TG 分发的唯一来源。

获取方式：在光鸭网页端进入对应目录，从地址栏 `parentId` / 目录 `fileId` 或浏览器开发者工具网络面板里 `get_file_list` 请求的 `parentId` 字段读取。留空或填 `*` 代表根目录，**生产环境建议填具体目录 ID**，避免把整个网盘当成 A 库遍历。

> **v0.8.1 起扫描根目录不用再填一遍；v0.8.3 起界面连输入框都已移除**：`_effective_scan_root()` 直接引用这里填的 B 库目录 ID（`ScanTask.root_id` / `.env SCAN_ROOT_ID` 只作兜底）。`GET /api/scan-task` 返回 `effective_root_id` 与 `root_source`，管理页「资源库 → 扫描计划」里只读展示。

> 待核实项：不同版本网页端地址栏参数名可能不同，以你实际看到的网络请求为准；本项目不提供目录 ID 自动枚举。

### 分类目录 1:1 镜像（v0.8.1）

A 库存在分类目录时，B 库按同样层级自动创建，**名字一个字都不改**：

```
A：动画电影 / 侠客行 (2001) {tmdb-135646} / Season 1 / E01.mkv
B：动画电影 / 侠·客·行 (2001) {tmdb-135646} / Season 1 / E01.mkv
     ↑ 分类原名        ↑ 只有影视主目录加 ·        ↑ 子目录原名
```

| 目录类型 | B 库命名 | `MirrorDir.kind` |
| --- | --- | --- |
| 分类目录（动画电影 / 国产电影 / 欧美电影 / 日韩电影…） | **原名，不加标记、不改名** | `category` |
| 影视主目录 | 按下方 `·` 规则 | `work` |
| 季目录 / 子目录（Season 1…） | 原名 | `season` |

- `MirrorDir` 表记录每个目录的 A→B 映射（`status=mapped/created/missing`），`GET /api/mirror/status` 返回 `dirs` 与 `missing_dirs` 清单。
- 默认开启「B 库缺目录自动创建」；关闭时只登记待创建目录、相关作品标 `blocked`（不是 `failed`），不会把整批作品打成失败。
- 识别分类目录靠「目录名线索 + 子树是否直接含视频 + 是否像作品名」，不再把 A 根目录的直接子目录一律当影视主目录。

### B 库影视主目录命名规则

**v0.8.3 起标记字符是 `·`，不是 `*`**：真实网盘 `create_dir` 返回 `code=141 msg=文件夹名包含非法字符: *`。只有 **B 库影视主目录的主标题段**插入 `·`：

```
A：大醉侠 (2002) {tmdb-135646}
B：大·醉·侠 (2002) {tmdb-135646}
```

- **括号里的年份、TMDB 标记保持原样，前面只用空格分隔，不加标记**。
- 中文按字符插 `·`；纯英文按**单词**插 `·`（避免逐字符乱码目录名）。
- 展示、资源库、分享标题、TG 推送全部用标准影视名（`standard_media_name()`），不会把带 `·` 的名字推给用户。
- 归一化时 `normalize_work_name()` 同时剥掉 `*` 与 `·` 和 `{tmdb-}` / 裸 `tmdb-` / `imdb-` 标记：旧带 `*` 名称就地转成 `·`；**v0.8.2 已降级创建的无标记目录会被归一化命中复用**，不会重复建目录或改名；A/B/无标记三种写法落到同一作品键。
- 分类目录直传 A 库原名，不经过标记剥离，**原名里带中点也不会被吃掉**。

### 镜像配置参数

| 参数 | 位置 | 说明 |
| --- | --- | --- |
| A / B 目录 ID | 镜像同步 → 设置 | 必填，缺失时「立即同步」直接报 400；B 库 ID 同时是扫描根目录 |
| 同步间隔 | 镜像同步 → 设置 | 按钮预设：10/15/30 分钟、1/2/6/12 小时、每天 |
| 启用 | 镜像同步 → 设置 | 关闭后定时任务注销，不自动同步 |
| `star_naming` | 镜像同步 → 设置 | B 库 `·` 命名模式开关（字段名沿用历史） |
| `auto_create_dirs` | 镜像同步 → 设置 | **v0.8.1**：B 库缺目录时自动创建（默认开） |
| `file_idle_seconds` | 镜像同步 → 设置 | **v0.8.1**：每个文件操作后的空闲秒数，默认 1.0，范围 `[0.5, 60]` |
| `min_idle_seconds` | 只读展示 | **硬下限 0.5 秒**，来自官方写接口 2 次/秒限频，人为不可调低 |
| `auto_identify` | 镜像同步 → 设置 | **v0.8.5**：同步完成后自动刷新资源库入库 → 识别 → 把本轮识别成功且有海报的影视按 TG 分发规则入队（默认开） |
| `rename_files` | 镜像同步 → 设置 | **v0.8.6**：把 B 库已同步的单集 / 单电影文件名按英文剧名改名（默认开）；关闭后自动同步不再改名，但手动「按英文规范改名」按钮仍可用 |

`file_idle_seconds` 对**每次复制、建目录、变化更新、文件改名**都生效；低于 0.5 秒后端直接返回 400。`get_task_status` 另有 0.2 秒轮询保护。

`GET /api/mirror/status` 可看到影视/文件映射数、目录映射数、自动创建目录数、待创建目录数、未知任务数、批次与变化事件数，以及已确认 / 待验证接口清单；同时回显 `config`（`auto_create_dirs` / `star_naming` / **`auto_identify`** / **`rename_files`** / A、B 目录 ID / 空闲时间），便于核对设置是否真的生效。v0.8.6 起还回显 `rename_errors[]`、`untranslated_works[]` 与 `counts.files_renamed` / `files_rename_failed` / `works_without_english`。

### 同步后自动入库识别并推送（v0.8.5）

> 行为变更：v0.8.0~v0.8.4 写死「镜像完成不自动推送 Telegram」，本版按用户明确要求反转。
> 但**镜像完成仍然不是群推送**。

链路：

```
A → B 复制完成（sync_rule + backfill_target_file_ids）
  → run_scan(B 库目录, resume=False) 刷新资源库入库
  → _post_scan_identify(publish_after_identify=True, limit=500)
  → 只把「本轮识别成功 + 有 TMDB 海报」的影视按启用的分发规则入队
  → 由既有 process_queue 逐条发送
```

| 约束 | 说明 |
| --- | --- |
| 手动 / 定时 | 两条路径都读 `auto_identify`；`POST /api/mirror/run` 不传 `post_identify` 时遵循开关 |
| 三态覆盖 | `post_identify=true` 强制、`false` 仅同步、不传按开关 |
| 推送闸门 | 沿用 v0.6.5：未识别 / 无海报绝不入队；`_enqueue_ready` 保证同作品同频道只一条 |
| 防群推 | 管线**不调用** `process_change_events`；历史 `queue_id=0` 的内容变化事件不被批量补推，返回值 `changes_pending` 只是只读计数 |
| 不做的事 | 不做对账删除、不重建/取消分享、不回溯推送历史已识别资源 |
| 返回 | `pipeline_enabled` 与 `pipeline{files, directories, complete, root_source, identify, queued, changes_pending}` |

内容变化更新仍由用户主动的「立即扫描 / 重新扫描库 / 定时扫描」按既有机制处理。关闭开关后，定时同步与「立即同步」都只复制文件，需要到资源库手动点「立即扫描」。定时任务的 `last_message` 会**追加**「[自动入库] 扫 N 文件 · 识别 N · 入队 N · 内容变化待处理 N」，不会覆盖 v0.8.4 的文件级复制错误诊断。

> **v0.8.2 / v0.8.3 排障**：`missing_dirs[].error` 是 `create_dir` 的真实报错，不再被通用文案覆盖。若 B 库根目录不可访问，同步会在开始时直接中止并给出含目录 ID 的提示。v0.8.3 起主目录直接用 `·`；**只有网盘连 `·` 也拒绝时**，才自动降级为不带标记的标准影视名（`MirrorDir.status=created_fallback`）。详见 `docs/后台功能使用说明.md` 第一节。

### B 库单集/电影文件英文改名（v0.8.6）

> 用户明确边界：**A 源头库不动、B 库影视文件夹命名不变，本次只优化单集 / 单电影文件名，且 A→B 映射必须保持，便于后期对比变量更新**。

| 项 | 说明 |
| --- | --- |
| 开关 | `rename_files`（镜像同步 → 设置，默认开）；与 `auto_identify` 互不干扰 |
| 自动触发 | `POST /api/mirror/run`、定时镜像、`POST /api/mirror/tasks/poll` 都在**扫描入库之前**对已同步文件改名 |
| 存量处理 | `POST /api/mirror/rename`（管理页「按英文规范改名」）；`force=true` 重新解析英文剧名（「重新解析英文名并改名」）。关闭自动开关后手动按钮仍可用 |
| 英文名来源 | 每部作品缓存一次：已识别 `Resource.original_title`（纯 ASCII）→ `tmdb.english_title()`（`language=en-US`）→ `ai_assist.translate_title()` 翻译；缓存落 `MirrorMedia.english_title` / `english_source` |
| 命名格式 | 只替换中文片名段；季集号 / 年份 / 画质 / 编码 / 压制组 / 扩展名原样保留。例：`大醉侠 第04集 2160p.WEB-DL.H.265.mkv` → `The Drunk Hero 第04集 2160p.WEB-DL.H.265.mkv` |
| 安全 | 目标名过滤网盘非法字符；同名冲突追加 `-vN`；原文件名无中文、英文名不可用或含中文时**一律不改** |
| 映射保持 | `MirrorFile.file_name` 恒为 A 原名，改名结果存 `target_name`；增量比对仍用 `source_file_id + fingerprint(size:utime)`；`_lookup_b_file()` 优先按 `target_name` 反查 B 库 `fileId`，改名不会导致重复复制 |
| 诊断 | `rename_status` / `rename_error` 落库；状态接口给 `rename_errors[]`、`untranslated_works[]` 与三个改名计数 |

改名与复制 / 建目录共用 `file_idle_seconds` 风控间隔。若「英文名待处理」清单里出现作品，先确认 TMDB 密钥有效或已配置 AI 翻译；解析不到时**不会**把中文原名硬塞进文件名。

### 改名状态以 B 库实际内容为准（v0.8.8）

v0.8.7 的空目录补复制会复用同一条 `MirrorFile` 行重新复制，复制回来的是 A 库中文原名；旧逻辑只重置 `target_file_id`，`rename_status=done` / `target_name=英文名` 残留会让改名整批跳过。v0.8.8 起：

| 情况 | 行为 |
| --- | --- |
| 补复制发生 | 同步清空 `target_name` / `rename_status` / `rename_error`，新文件一律待改名 |
| B 库列目录显示当前名已是目标英文名 | 跳过并把 DB 状态纠正为 `done`，不重复调 `rename_file` |
| B 库当前名仍是中文（或其它非目标名） | 无论 DB 写的是什么都重新改名 |
| 列目录失败 / 分页不完整 | 退回 DB 幂等判断，防接口抖动误改 |

`fileId` 也优先取 B 库列目录命中值，DB 的 `target_file_id` 仅在列目录失败时兜底。同步结果提示会给出「已达标跳过 / 无中文跳过 / 无待改名文件 / 首个改名错误」，整体异常另写进 `rule.last_message`，刷新「同步状态」页仍可见。

### 文件复制状态与排障（v0.8.4）

`GET /api/mirror/status` 新增 `file_errors[]`（最近 50 条，含作品名 / 文件名 / 任务 ID / 真实报错）与 `counts.files_failed` / `files_copying` / `files_unknown` / `files_retryable` / `tasks_failed`。`rule.last_message` 也会追加「复制失败 N · 首个文件错误：…」，刷新页面仍可见。

复制链路的状态机：

| `MirrorFile.status` | 下一轮行为 |
| --- | --- |
| `synced` | 判为未变，不再复制 |
| `pending` / `copying` / `failed` / `unknown` | **复用同一行重新发起 `copy_file`**；重试前先只读列 B 库，若同名同大小文件已存在则回填 `target_file_id` 并纠正为 `synced`，不重复复制 |
| `superseded` | 历史版本，跳过（受日志保留策略清理） |

`get_task_status` 按网页端 JS 的真实语义判定：`status=2` 且无 `detail.code` 为完成；`status=3` 或 `status=2` 且 `detail.code≠0`（如 157 云盘空间不足）为明确失败，写入 `MirrorTask.error` / `MirrorFile.error`。其它取值仍是 `unknown`，保留 taskId 供「轮询任务」继续查询。

列目录请求体已与 `w.har` 对齐：`{pageSize:50, orderBy:3, sortType:1, parentId, page:0}`，分页按累计条数与 `total` 比对，短页但 `total` 更大时判为不完整并中止，避免用残缺批次做同步决策。

> **接口取证边界**：`copy_file` 目前只有前端 JS 调用契约，原始 `w.har` 里**没有一次真实复制请求**。若「文件复制失败」清单里全部指向 `copy_file`，请在网页端手动执行一次「复制到」并抓包复核，详见 `docs/光鸭接口取证.md` 第十节。

### B 库存在性核对与空目录自愈（v0.8.7）

v0.8.4 修的是「`copying` / `failed` / `unknown` 被当成 unchanged」，v0.8.7 补上另一半：**DB 标记 `synced` 不等于 B 库真的有文件**。每轮同步对每部作品只读递归列一次 B 库目录树：

| 情况 | 行为 |
| --- | --- |
| 列目录完整可信 + 确实找不到文件 | 复用同一 `MirrorFile` 行重置为 `pending` 自动重新复制，`file_name` 仍是 A 原名，A→B 映射不丢 |
| 列目录异常 / 分页不完整 / 目录层级超 60 | 一律不动 `synced`，防接口抖动重复复制 |
| B 库文件数 ≥ 已同步记录数 | 绝不重置，只记 `name_mismatch`（多半是网盘改名 / 重名加后缀） |
| `作品/Season 1/1080p/` 多层结构 | 递归遍历必须找到，不误判为空而重复复制整部作品 |

`stats` 新增 `missing_in_b` / `name_mismatch`，同步结果提示与 `rule.last_message` 会显示「B库缺失补复制 N · 名称不符 N」，文件级原因进 `file_errors[]`。补复制同样遵守 `file_idle_seconds`（硬下限 0.5 秒）。

### 资源库刷新三入口（v0.8.7）

`POST /api/library/refresh`（顶部「刷新」）、`POST /api/scan-now`（立即扫描）、`POST /api/library/rescan`（重新扫描库）共用同一重建管线，定义都是「读取最新 B 库内容 → 按实际内容重建面板」。用户主动刷新允许**可信空批次**清库（批次 success + complete + 非断点 + `directories>0` + `seen_count=0`）；定时扫描与镜像后管线不做对账删除，也不群推。

## 三、TgtoDrive OpenAPI 配置

TgtoDrive 是**独立外部系统**：Ya-TG 不集成它的源码、不部署它的容器、不读写它的数据库，只通过 OpenAPI 读写关键词规则。

管理页「互动中心 → TgtoDrive」填写：

| 配置键 | 说明 |
| --- | --- |
| `tgto_base_url` | TgtoDrive 服务根地址，例如 `http://<NAS内网IP>:<端口>`，末尾不要带 `/` |
| `tgto_api_key` | OpenAPI Token，鉴权头 `Authorization: Bearer <token>` |
| `tgto_scene` | 场景名，默认 `ENV_FILTER_GUANGYA` |
| `contribution_enabled` / `contribution_bot_token` | 投稿 Bot 开关与 Token |
| `donation_enabled` / `donation_image_url` / `donation_text` / `donation_button_text` | 打赏展示配置 |

所有配置走运行时加密落库，已登记进 `runtime_config.DEFAULTS`，不会出现「保存了但被静默忽略」。

### 接口与合并策略

```http
GET  {base}/api/visual-filter/config?scene=ENV_FILTER_GUANGYA
POST {base}/api/visual-filter/config
```

接口结构来自仓库同级 `tgto-openapi.json` 与 `guangya_visual_filter.json` 的实证。因为该接口**没有单条增删**，只能全量覆盖，Ya-TG 采取严格保守策略：

1. **GET 全量** → 2. 内存里只合并目标规则 → 3. **POST 回写** → 4. **回读校验**
5. 规则 id 用幂等格式 `kw_<tmdb_id>_<season>`（无 TMDB ID 时用 `kw_ya-tg_<标题slug>`）
6. 只新增或更新 `source=ya-tg` 的同 id 规则；**同 id 已存在且属于其它来源，直接返回 `conflict`，一次都不写回**，原有关键词、管理员手动规则、其它项目规则全部保留

「互动中心 → 测试连接」走 `POST /api/tgto/test`，只做只读探测，不会改动对方配置。

## 四、互动 Bot 配置

投稿 Bot 用 Telegram 官方 `getUpdates` / `sendMessage`，**不依赖光鸭抓包**。

1. 找 @BotFather 创建独立 Bot，拿 Token（建议与分发用的 Bot 分开）。
2. 「互动中心」填 `contribution_bot_token`，开启 `contribution_enabled`。
3. 「立即轮询」触发一次 `POST /api/bot/poll`；系统按 `contribution_update_offset` 增量拉取，不重复处理。

支持指令：

```
/want 剧名 [TMDB ID] [季]   提交想看的影视，自动合并关键词监控规则
/contribute 标题 [分享链接] 投稿资源，登记为 pending，由管理员审核
/donate                     查看打赏信息
/help                       查看说明
```

普通文本里带链接也会登记为投稿。投稿**只写 `user_contributions`，状态 `pending`**，不自动转存、不写 B 库、不触发任何推送；审核入口在「互动中心 → 投稿列表」。

## 五、.env 配置项

`.env.example` 保持极简，普通用户只需两项：

| 项 | 说明 |
| --- | --- |
| `ADMIN_PASSWORD` | 管理后台登录密码 |
| `APP_SECRET` | Fernet 加密主密钥，`openssl rand -hex 32` 生成 |
| `IMAGE_TAG` | 留空 = latest；锁版本填 `v0.8.8` |
| `WEB_PORT` / `WEB_BIND` | 网页端口与绑定地址 |
| `AUTO_CREATE_SHARE` / `SHARE_DURATION` | 分享策略 |
| `SCAN_CRON` / `SCAN_ROOT_ID` | 扫描计划（管理页改间隔按钮会覆盖 Cron；根目录以 B 库 ID 为准） |
| `TMDB_*` / `AI_*` | 可选，推荐在管理页填 |
| `TELEGRAM_API_BASE` | 可选，国内网络可填反代地址 |

`.env.example` 文末以注释形式保留 `GUANGYA_*` 高级凭证，普通用户不要填写。`tgto_*` / `contribution_*` / `donation_*` / v0.8.1 的 `file_idle_seconds` / `auto_create_dirs` **一律在管理页配置，`.env` 里没有也不需要这些项**。

数据库卷固定 `./db:/app/db`，`DATABASE_URL=sqlite:////app/db/ya-tg.db`；升级时**不要删 `db/` 目录**。v0.8.1 首次启动会自动补 `mirror_rules.file_idle_seconds` / `auto_create_dirs`、`mirror_media.category_path` 三列并新建 `mirror_dirs` 表。

## 日志保留配置（v0.8.3）

全部在管理页「操作审计 → 日志保留与清理」配置，运行时加密落库，改完即时生效，**不新增 `.env` 项**。

| 配置 | 默认值 | 范围 | 说明 |
| --- | --- | --- | --- |
| `log_retention_days` | 30 | 1–3650 | 超过该天数的历史日志自动清理 |
| `log_max_rows` | 5000 | 100–200000 | 每类日志超出上限时从最旧的记录开始删 |
| `log_auto_prune` | `true` | 开/关 | 启动时 + 每天 03:30（Asia/Shanghai）自动清理；关闭后只能手动清理 |

接口：`GET /api/logs/overview`（各类条数、时间跨度、保护规则）、`POST /api/logs/config`、`POST /api/logs/prune`、`POST /api/logs/clear`（需 `confirm=true`）。

**绝不误删**：running 扫描批次、pending/running 镜像任务、`queue_id=0` 的待处理分发事件、pending/retry/review 队列项、非 `superseded` 的文件映射一律保留；资源、目录映射与分享链接不在清理范围。容器 stdout 日志另由 compose 的 `json-file` 限额 `3 × 10MB` 控制。

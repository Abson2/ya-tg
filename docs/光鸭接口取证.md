## 五、限频与风控依据

- 官方 OpenAPI v1.3 §10：写接口 **2 次/秒**限频；文件列表接口 5 次/秒。
- 因此项目设 `MIN_FILE_IDLE_SECONDS = 0.5` 为**硬下限，人为不可调低**：`MirrorRule.file_idle_seconds` 只能调高（默认 1.0 秒，上限 60 秒），前端 `min` 与后端 400 校验双重约束。
- 每次 `copy_file` / `create_dir` / 变化更新前按 `max(配置值, 0.5)` 等待；`get_task_status` 另有 0.2 秒轮询保护；任务先批量提交再统一等待，避免逐条阻塞。

## 八、`create_dir` 在真实环境的失败排查（v0.8.2）

HAR 里 `create_dir` 是在网页端手工新建文件夹时抓到的，返回 `200 / msg=success / data.fileId`。但镜像同步实际调用时，B 库目录 ID、写入权限、目录名字符都可能与抓包场景不同。v0.8.2 之前这些错误会被界面通用文案吞掉，导致「42 部作品全 missing、看不出为什么」。

现在的处理链路：

1. `sync_rule()` 先用 `get_file_list` 预检 B 库根目录；不可读直接抛 `WebFileError`，消息含 B 库目录 ID 与接口原始错误，**不会**逐部作品试建目录。
2. `_ensure_child()` 调 `create_dir`，失败原因写入 `MirrorDir.error`，并进 `stats["dir_errors"]` / `rule.last_message` / 容器日志 `[mirror]`。
3. `/api/mirror/status` 把 `error` 原样回显到「待创建目录 → 失败原因」，同时返回 `config` 回显开关与目录 ID。
4. 若报错与目录名有关（例如网盘拒绝 `*`），自动用不带 `*` 的标准影视名重试一次，成功后整轮沿用标准名，标记 `created_fallback`。

排障时请提供：`docker compose logs --no-color --since 1h ya-tg > ya-tg.log 2>&1` 生成的日志，或管理页「同步状态 → 生效配置」+「待创建目录 → 失败原因」两处截图。**不要把原始 HAR 或未脱敏日志直接发出去。**

## 九、`code=141 文件夹名包含非法字符: *`（v0.8.3 真实返回）

用户在真实网盘确认了 v0.8.2 降级提示的来源：

```text
POST /userres/v1/file/create_dir
响应：code=141  msg=文件夹名包含非法字符: *
```

- 这不是 B 库目录 ID 错误，也不是登录态失效，而是**网盘禁止目录名里的 `*`**。v0.8.2 的降级因此创建出「不带标记的标准影视名」目录。
- v0.8.3 按用户要求把标记字符换成 `·`：`大醉侠 (2002) {tmdb-135646}` → `大·醉·侠 (2002) {tmdb-135646}`；括号年份与 `{tmdb-}` 标记不动，分类目录保持原名。
- 兼容性：`standard_media_name()` / `normalize_work_name()` 同时识别 `*` 与 `·`，旧 `*` 名称就地转 `·`；**v0.8.2 已创建的无标记目录会被归一化命中复用**，既不重复建目录，也不调用 `rename`（主链路依旧不改名存量目录）。
- 保底：只有网盘连 `·` 也拒绝时，才降级为无标记标准名并写 `MirrorDir.status=created_fallback`，真实报错照常落到「待创建目录 → 失败原因」。
- 本版没有新增抓包接口；`create_dir` 的请求/响应结构仍以第一节的 HAR 为准。

## 十、文件复制链路取证（v0.8.4）：`copy_file` 只有 JS 契约，没有真实请求

用户反馈 v0.8.3 真实环境「**影视目录的文件夹创建正常、命名正常，对应的文件没有镜像过去**」。复查原始 `w.har`（54 条请求）得到关键结论：

| 接口 | 证据等级 | 说明 |
| --- | --- | --- |
| `create_dir` / `rename` / `delete_file` / `get_file_list` / `get_task_status` | ✅ HAR 真实请求 + 响应 | 目录能建、命名正常，与用户现象吻合 |
| `copy_file` | ⚠️ **仅前端 JS 调用代码** | 54 条请求里没有任何一次复制操作，只有 JS bundle 中的路径字符串与调用片段 |
| 投稿分享转存 | ❌ 未实现 | 无抓包、无 JS 证据 |

### 已确认的契约（来自 `index.4998cfbcbd.js`，非抓包响应）

```javascript
// onCopyTo
let l = a.map(e => e.fileId);
let { key: n } = (await Ay.show({ title: "复制到" })).data;
let t = await gL("/userres/v1/file/copy_file",
                 { method: "POST", body: { fileIds: l, parentId: n } });
await p3(t.data.taskId, {...}, { taskSource: "copy_file" });
```

即 `POST /userres/v1/file/copy_file {fileIds:[...], parentId}` → `data.taskId`，与本项目 `GuangYaWebFiles.copy_file()` 的实现一致。`taskSource` 只用于前端错误提示，**不发给后端**（HAR 中 `get_task_status` 的真实请求体只有 `{taskId}`）。

### 任务状态语义（JS 轮询函数 `p5`）

```javascript
let a = await cJ({ taskId: e });       // cJ = get_task_status
let i = a.data.status, n = a.data.detail?.code;
if ([2,3].includes(i) && n && n !== 0) throw 任务失败(detail.msg, n);
if (2 === i) return { result: "success", ret: 0 };
if (3 === i) throw 任务失败(detail.msg, -1);
```

`w.har` 中两次 `get_task_status` 真实响应均为 `{"msg":"success","data":{"status":2}}`。v0.8.3 只认 `status=2`、丢弃 `data.detail`，会把 `status=3` 或 `detail.code=157`（云盘空间不足）误记成「待确认」，`MirrorFile` 永远停在 `copying` 且下一轮被视为已存在而跳过——这正是「空文件夹且反复同步无效」的代码层根因。v0.8.4 已按上述语义修正并加入自动重试。

## 十一、`rename` 在 v0.8.6 的正式用途（B 库文件改名）

第二节第 2 条的 `POST /userres/v1/file/rename {fileId,newName}` 在 `w.har` 里已有真实请求+响应取证。v0.8.0~v0.8.5 只把它作为「已实现但主链路不调用」的能力（目录直接按目标名 `create_dir`，不需要先建后改名）；**v0.8.6 起才正式用于 B 镜像库的单集 / 单电影文件改名**。

| 约束 | 说明 |
| --- | --- |
| 调用对象 | `fileId` **必须是 B 库文件**。A 源头库全程只读，代码里绝不传 A 的 `fileId`；`rename_file()` docstring 已写明 |
| 不改的东西 | B 库分类目录（A 原名 1:1）、影视主目录（`·` 命名）、季目录一律不改名 |
| 新名字来源 | TMDB `en-US` 官方片名 → 已识别 `Resource.original_title` → AI 翻译；`file_naming.py` 只替换中文片名段，并清洗网盘非法字符（斜杠 / 冒号 / 星号 / 问号 / 引号 / 尖括号 / 竖线） |
| 幂等 / 冲突 | 目标名已改过就跳过；B 库同名且非同一 `fileId` 时追加 `-vN` |
| 映射保持 | `MirrorFile.file_name` 恒为 A 原名，改名结果存 `target_name`；`_lookup_b_file()` 优先按 `target_name` 反查，改名不会导致下轮重复复制 |
| 风控 | 文件之间沿用 `file_idle_seconds`（硬下限 0.5 秒） |

**仍待真实环境确认**：`w.har` 里的 `rename` 样本改的是普通文件名，未见中文→英文长文件名（含 `2160p.WEB-DL.H.265` 等压制组后缀）的真实返回；若网盘对文件名也有类似 `code=141` 的非法字符拒绝，报错会落进 `MirrorFile.rename_error` 并显示在管理页「改名失败」清单，不会静默吞掉。建议升级后先小批量点一次「按英文规范改名」实测。

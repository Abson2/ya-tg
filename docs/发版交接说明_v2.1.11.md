- 批次 running/paused 时一律 **409 拒绝**。
- 配套归档机制：`backend/app/archive.py`（`find_resource_by_file_id` / `find_queue_item` 命中归档行时复活复用，避免唯一键冲突）。

## 三、本轮修掉的缺陷（含我自己引入的）

1. **归档过滤漏掉 `count()` / `exists()` / 子查询（结构性缺陷）**
   - 现象：`db.query(Resource).count()` 返回 2（应 1），`.all()` 返回 1——同一张表两个口径。
   - 根因：旧实现只看 statement 顶层 from；`Query.count()` 走 `_legacy_from_self()` 把查询包成匿名子查询，真表在里层。
   - 修法（`backend/app/db.py::_install_archive_filter`）：递归下钻 + **自内向外逐层打补丁**。用 `visitors.iterate` 找全部 Select → `_needs_patch()` 判定该层是否引用目标表且未打补丁 → `_pending_children()` 判定内层是否还有待打补丁子节点 → 每轮只处理「内层已收敛」的那一层 → `replacement_traverse` 替换 → 循环至收敛（上限 8 层）。
   - **API 事实（SQLAlchemy 2.0.38）**：`Query.with_criteria` / `Select.with_only_criteria` **不存在**；`visitors.replacement_traverse(obj, opts, replace)` 签名三个参数；`replace` 回调返回非 None 会 `stop_on.add(id(newelem))` 停止下钻 → 必须**自内向外逐层**打补丁；`Select.where()` 是 `@_generative`（返回新对象）；criterion 对象身份在克隆后仍保留（`is` 判定可靠）。
   - 15 项行为探针全部验证通过。

2. **`/api/mirror/mappings/prune` 端点被整体替换掉了**（我引入的真回归，违反红线「不得删按钮/端点」）
   - 修法：恢复端点，薄封装转发到统一端点 `scope=all`；并新增守卫用例 `test_backend_prune_endpoint_still_exists`。

3. **前端出现后端字段名 `media_invalid`**（我引入的红线违规）
   - 修法：后端加中文口径别名 `invalid_mappings` / `unmapped_dirs`；前端改用别名。

4. **前端「清理无效映射」点下去直接 400**
   - 根因：`pruneMirrorMappings()` 调 `runMirrorCleanup('all')`，但后端 scope 白名单只有 `file|dir|pruned|media`。
   - 修法：白名单补 `all`（`prune_stale_mappings` 本身支持 `scope="all"`）。

5. **`clear-pruned` 薄封装返回未 await 的协程**（我引入的真回归）
   - 现象：pytest 报 `RuntimeWarning: coroutine 'mirror_cleanup' was never awaited`，实际什么都没删。
   - 根因：老端点是**同步**函数（历史测试与内部调用方直接同步调用），转发到 async 端点就返回协程对象。
   - 修法：把 scope=pruned 的逻辑抽成**同步**函数 `_cleanup_pruned_dirs(db, rule_id, ids, dry_run)`，统一端点与老端点共用。

6. **resume 语义真回归**
   - 现象：running 状态下 `resume` 不再清指令 → 用户无法撤销误点的「跳过当前」。
   - 修法：恢复旧语义——resume **无条件清掉待消费的一次性指令**；paused/cancelling 时同时恢复 running。

7. **清理确认文案误导**
   - 现象：三个清理按钮共用一段「只会被重置为待同步」话术，但其中两个实际是**物理删行**。
   - 修法：确认文案按 scope 分化，各自说清真实后果；先 `dry_run` 预览再执行。
